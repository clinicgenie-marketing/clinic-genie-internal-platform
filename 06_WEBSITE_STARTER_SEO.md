# Website starter, SEO soft launch and migration

## Website foundation
Inspect existing code before selecting a framework. Reuse compatible components and deploy each clinic independently through configuration. Public pages follow each clinic's approved brand; Clinic Genie admin colours must not overwrite client branding. No custom CMS/editor in Phase 1.

Confirm required pages during discovery. Use a minimal demonstration page set until the clinic approves actual content. Optimise images and use semantic headings, labels, keyboard navigation, responsive layouts and visible focus states.

## Existing SEO foundation
- The `clinic-demo-a` Next.js site already generates page-specific title, description, canonical, Open Graph and robots metadata from code.
- `sitemap.ts` lists the site's configured routes and only emits URLs for an explicitly public deployment with a configured base URL.
- `robots.ts` blocks indexing on previews and emits safe public defaults when indexing is enabled.
- Preserve all existing structured data and SEO output. Do not fabricate clinic or practitioner facts.

## Authorized SEO soft-launch scope
Implement only the following in the first soft launch:

1. Basic per-page title, meta description, canonical path and indexability settings, connected to generated public HTML.
2. Individual searchable/editable permanent 301 redirects for supported code-managed sites. Require local paths, reject self-redirects and loops, and keep inactive records out of the public output.
3. A setup checklist that reports only saved/configured facts. Clearly distinguish "ready", "staff marked" and "not verified"; the platform does not crawl the site or claim Google indexing.
4. Automatic XML sitemaps using the supported site's route inventory, respecting canonical paths and page-level noindex settings.
5. Generated robots.txt defaults that disallow previews and identify the sitemap for public deployments.
6. Google Search Console HTML meta-tag verification support. Publishing the tag does not verify site ownership; an authorised person must complete that step in Search Console.
7. Google Business Profile references per client branch, a manually maintained setup status, and safe links to open the profile or Google Business Profile manager.

Keep existing SEO content/search mapping and structured data intact. No Wix or other external platform is assumed editable. Only websites whose platform is explicitly identified as a supported Next.js site may use the published-settings connection.

## Admin-to-site publishing boundary
The Genie Works SEO module and clinic websites are separate apps and databases. The soft launch uses a site-scoped authenticated, read-only published-settings API:

- Genie Works stores the editable SEO values and exposes `/api/public/seo/{websiteId}` using a per-website bearer token whose hash is stored in the database.
- A supported public Next.js deployment receives `SEO_SETTINGS_API_URL`, `SEO_WEBSITE_ID` and `SEO_SETTINGS_API_TOKEN` as server-only deployment environment variables. The raw token is generated once in Genie Works and is not put in browser code.
- Saving a page setting publishes it immediately. The public site consumes page metadata, active redirects and the Search Console token with a short cache lifetime; redirects are applied as HTTP 301 responses.
- If the API is not configured or unavailable, the public site continues using its code-defined metadata and existing SEO behavior; it does not invent a redirect or claim the new values were published.
- Each website is separately connected. Do not infer support from the domain, provider account reference, or a Wix listing. Wix-hosted sites remain unchanged unless a separate supported integration is explicitly approved.

Required deployment inputs are the deployed Genie Works API origin, the website UUID from the registry, and a generated per-site token. The public site URL and indexing opt-in remain separately configured.

## Soft-launch checklist statuses
- **Page settings:** configured when an override is saved; public HTML output must be checked before launch.
- **Redirects:** ready when the route is connected and rules are saved; verify status codes and destinations on the deployed host.
- **Sitemap / robots:** generated by the supported site code; check the deployed responses and public-indexing setting. These are not automatic evidence of indexing.
- **Search Console:** code configured means the HTML tag can be emitted; ownership is pending until confirmed by an authorised Search Console user.
- **Business Profile:** branch reference and setup status are staff-entered; "staff marked verified" is not Google API validation.

## Deferred after first soft launch
Bulk redirects, redirect groups, advanced metadata templates, automated Site Inspection, direct Google Business Profile API management, performance reporting, `llms.txt` and NLWeb stay in the backlog. Do not create empty screens for them.

## SEO QA checklist
- Page-specific title, description, canonical, clean route and clear primary heading.
- Verified structured data consistent with visible content; no fabricated practitioner facts.
- Sitemap contains intended public indexable canonical pages; proper robots rules.
- Unknown routes return a real 404 status; redirects are checked for loops and wrong destinations.
- Preview environments use access protection and appropriate indexing controls. Robots alone is not access control.
- Mobile layout, alt text, accessible forms and performance checks have evidence.

## Publishing
Content changes use source control and preview deployment. Link approved medical copy/version to release evidence. Review changed SEO output before production. Record release commit, approver and rollback reference.

## Migration gate
Prefer a new website pilot. For Wix migration, add a dedicated ticket: inventory existing URLs/content, baseline GA4/GSC, preserve valuable pages, map redirects, compare staged output, obtain approval and monitor live indexing/404s. Re-estimate rather than hide migration work inside the template ticket.
